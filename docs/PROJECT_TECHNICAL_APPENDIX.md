# Relay：面向应用生成的多 Agent 协作系统（技术附录）

> 本文是一份技术方案与演进规划说明。文中会明确区分当前已经实现的能力、仅完成原型验证的能力，以及后续计划建设的能力。

## 1. 项目概述

Relay 是一个面向应用原型生成场景的多 Agent 协作系统。用户输入自然语言需求后，系统根据任务复杂度组织不同角色完成需求分析、调研、架构设计、代码生成和质量审查，并通过实时事件流展示执行过程，最终交付可预览、可导出、可继续修改的前端应用。

这个项目关注的核心问题不是“如何再封装一次模型调用”，而是：

- 如何把开放式需求转化为可执行的任务图；
- 如何让不同 Agent 通过明确契约协作，而不是无约束地互相聊天；
- 如何在模型输出不稳定的前提下，保证流程可观察、可暂停、可恢复；
- 如何管理上下文、工具、技能、文件和版本；
- 如何逐步演进为可扩展的 Agent Runtime。

当前版本完成了多 Agent 工作流的 MVP，可以演示从需求输入到代码生成的主链路；但它还不是完整的通用 Agent Runtime。Memory、RAG、工具运行时、真正的多轮对话、任意时刻中断恢复等能力仍属于后续规划。

## 3. Agent 角色设计

当前系统没有让一个模型同时承担产品、架构、编码和验收职责，而是按交付物边界拆分为六类 Agent。

| Agent | 职责 | 主要输入 | 主要输出 |
|---|---|---|---|
| Director | 理解需求、判断复杂度、决定是否需要澄清 | 用户需求 | 路由结果、澄清问题 |
| Strategist | 把模糊需求转成产品规格 | 用户需求、路由结果 | `brief` |
| Scout | 补充调研信息和参考方向 | 用户需求 | `report` |
| Architect | 设计页面、数据实体和模块关系 | `brief`、`report` | `blueprint` |
| Maker | 生成代码、应用补丁、按审查意见修复 | 需求及上游产物 | Workspace 文件 |
| Auditor | 独立检查交付物并给出修复要求 | 规格、代码 | `review` |

角色拆分的依据不是拟人化展示，而是上下文和责任边界：每个 Agent 只获取完成其任务所需的信息，并产出下游能够消费的结构化结果。

## 4. Graph 与多 Agent 编排

### 4.1 当前 Graph Type

当前实现采用“代码定义的半动态任务图”，不是完全由模型自由生成 Graph。

系统内置三种工作流：

- `sketch`：Maker 直接生成，适合快速原型；
- `workshop`：Director 分流后动态展开多 Agent 流程；
- `expedition`：Scout 先调研，经过人工确认后再由 Maker 生成。

`workshop` 中存在两种条件分支：

- 简单任务：`Director → Maker → Auditor`
- 复杂任务：`Director → (Strategist || Scout) → Architect → Maker → Auditor`

其中 Strategist 和 Scout 使用并行 wave 执行；Architect 等待两者完成后再开始。Auditor 如果返回 `needs_fix`，会进入最多两轮的 `Maker → Auditor` 修复循环。

因此当前 Graph 已经覆盖：

- 顺序节点；
- 条件分支；
- 并行节点；
- 依赖汇合；
- 有界循环；
- 人工确认节点；
- 状态持久化后的断点继续。

但它仍是受限 Graph：节点类型、依赖关系和循环上限主要由代码预定义，尚不支持模型按任务实时生成任意执行图。

### 4.2 为什么先采用确定性编排

让 LLM 自由决定下一步具有灵活性，但会引入不可预测循环、成本失控、错误路由和难以测试的问题。当前版本将职责拆成两层：

- Python Orchestrator 负责状态机、依赖、并发、暂停、重试边界和持久化；
- LLM 只负责需要语义判断或内容生成的节点。

这个取舍牺牲了一部分通用性，但换来了 Demo 阶段更重要的可解释性和可控性。后续不会简单替换为“全动态”，而会演进为静态 Graph、模板 Graph 和动态 Graph 并存。

## 5. Agent Runtime

### 5.1 当前实现

当前 Orchestrator 已具备轻量 Agent Runtime 的雏形：

- 根据 pipeline cursor 顺序调度节点；
- 记录节点状态和会话阶段；
- 使用 AsyncIO 并行执行同一 wave 中的 Agent；
- 统一产生 `agent_start`、`delta`、`artifact`、`verify`、`agent_done` 等事件；
- 将 Agent 产物写入 artifacts、messages 或 workspace；
- 捕获模型致命错误与普通运行错误；
- 在澄清或 checkpoint 处暂停，用户输入后继续；
- 服务重启后通过持久化的 pipeline 和 cursor 恢复既有流程。

### 5.2 当前限制

它还缺少正式 Runtime 应具备的能力：

- 统一的 Agent 执行接口和生命周期钩子；
- 节点级超时、重试、退避和熔断策略；
- 用户主动取消与任意时刻暂停；
- 幂等键和重复请求处理；
- 跨进程任务队列和 Worker；
- 资源配额、并发限制和优先级调度；
- Agent 运行沙箱；
- 统一 trace、token、成本和延迟指标。

## 6. 意图识别与多轮交互

### 6.1 当前实现

首次需求进入 Director 后，可以识别信息是否足够并产生结构化澄清问题。用户提交补充信息后，系统将答案合并到原始需求，清空原 pipeline，并重新进入分流流程。

项目生成完成后，前端也支持向 `/iterate` 提交修改指令，由 Maker 尝试补丁修改；失败时回退为全量重写。

### 6.2 未完成部分

当前“迭代修改”不等于真正的多轮对话。系统尚未统一识别后续输入属于：

- 普通问答；
- 需求补充；
- 项目修改；
- 状态查询；
- 工具操作；
- 版本回滚；
- 暂停、取消或恢复指令。

当前后续输入主要被直接当作代码修改指令，完整消息历史也没有经过专门的上下文构建器传给模型。因此多轮意图路由和连续对话应列为 P0，而不能描述为已经完成。

## 7. Tools Runtime

### 7.1 当前状态

当前系统具备文件读取、写入、补丁应用、快照、回滚、导出和模型调用等内部函数，但它们由业务代码直接调用，还没有抽象成独立 Tools Runtime。

### 7.2 目标设计

后续 Tools Runtime 应提供：

- Tool Registry：工具名称、描述、参数 Schema 和版本；
- Tool Policy：不同 Agent 可调用的工具白名单；
- 参数校验：执行前基于 Schema 验证；
- 执行控制：超时、重试、取消、并发和速率限制；
- 权限确认：高风险写操作进入人工审批；
- 结果标准化：统一成功、错误和元数据结构；
- 可观测性：记录调用者、参数摘要、耗时和结果；
- 隔离性：文件、命令和网络工具在受限环境运行；
- 幂等性：避免重试导致重复写入或重复外部操作。

工具调用应成为 Runtime 的一级事件，而不是隐藏在 Agent 内部的副作用。

## 8. Skills 集成

### 8.1 当前实现

当前支持以 Markdown 定义 Skill，包含目标 Agent、关键词和说明内容。系统可以：

- 加载内置和用户 Skill；
- 校验并安装用户 Skill；
- 启用、停用和删除 Skill；
- 根据 Agent ID 和关键词匹配 Skill；
- 将命中的 Skill 说明注入该 Agent 的 system prompt。

### 8.2 当前限制与规划

目前 Skills 本质上是“可管理的 Prompt 片段”，还不是完整能力包。后续需要增加：

- Skill 版本、来源、依赖和兼容信息；
- 多 Skill 冲突检测与优先级；
- Skill 的渐进式加载，减少无关上下文；
- Skill 绑定工具权限和输出 Schema；
- Skill 执行前置条件与验收规则；
- Skill 使用效果评测；
- Skill 缓存、发布、回滚和审计；
- 将静态关键词匹配升级为语义检索与路由。

## 9. Memory、RAG 与上下文压缩

### 9.1 当前状态

当前系统保存了会话元数据、消息、pipeline、结构化 artifacts 和 workspace 文件，因此已经具备“可恢复状态”，但尚未形成完整 Memory 系统。

现有上下文控制主要依赖：

- 只给不同 Agent 传递相关 artifact；
- 对文件内容做固定字符截断；
- 使用简短结论替代部分原始输出。

这能控制 Demo 成本，但会丢失早期约束，也无法根据问题检索最相关的信息。

### 9.2 目标 Memory 分层

后续将 Memory 拆为四层：

1. Working Memory：当前节点需要的输入、临时推理结果和工具返回；
2. Conversation Memory：同一会话的用户消息、助手回复和人工决策；
3. Project Memory：需求、架构决策、文件摘要、版本变更和已知问题；
4. User Memory：经用户授权保存的偏好、技术栈和常用约束。

Memory 写入需要经过提取和去重，不能把所有原始文本无限累积。

### 9.3 RAG 规划

RAG 的检索对象包括：

- 生成项目的代码和文档；
- 历史 Agent 产物；
- 会话决策与需求变更；
- Skill 文档；
- 平台规范和参考模板。

计划采用“结构化过滤 + 语义召回 + 重排”：

1. 按 session、文件类型、Agent、版本和时间过滤；
2. 使用 embedding 召回候选片段；
3. 结合关键词、依赖关系和新鲜度重排；
4. 将引用来源随上下文一起交给 Agent；
5. 记录检索命中，支持调试回答依据。

### 9.4 上下文压缩

上下文构建器需要管理明确的 token budget：

- 保留最近对话原文；
- 将较早对话压缩为可更新摘要；
- 对代码按符号和依赖切片，而不是简单截断；
- 保留不可丢失约束，如验收标准和用户否决项；
- 对重复工具结果去重；
- 为不同 Agent 分配不同上下文视图；
- 当压缩可能损失关键信息时触发人工确认。

## 10. Human-in-the-loop 与执行控制

### 10.1 当前实现

当前已经实现两类人工介入：

- Director 判断信息不足时发出澄清问题，用户补充后恢复；
- checkpoint 节点暂停执行，等待用户决定继续或停止。

这些状态会写入 `pending.json`，pipeline cursor 和阶段也会持久化，因此属于“预设位置的暂停与恢复”。

### 10.2 后续目标

完整 Human-in-the-loop 还需要支持：

- 用户在任意节点主动暂停；
- 执行过程中追加信息，并决定应用于当前节点还是后续节点；
- 用户取消任务并终止仍在运行的模型或工具；
- 高风险工具调用前审批；
- 修改 Agent 计划、跳过节点或要求重做；
- Agent 在低置信度时主动请求人工决策；
- 中断时保存 checkpoint，恢复时避免重复副作用；
- 用户在任务执行期间提问，Runtime 能回复状态而不破坏主任务；
- 对审批、修改和恢复操作保留审计记录。

实现上需要把“任务控制消息”和“业务对话消息”分开，并为每次运行分配 run ID、状态版本和取消令牌。

## 11. 文件、版本与结果验证

当前 Maker 支持两种生成策略：

- 全量生成：适合首次交付或补丁无法可靠应用时；
- 补丁修改：通过 search/replace 降低小改动的 token 和覆盖风险。

每次迭代前可以创建 workspace 快照，前端能够列出快照并回滚。Auditor 会检查产物，失败时触发最多两轮修复。

当前版本体系仍较基础：

- 快照缺少完整的时间、说明、来源 run 和变更摘要；
- 没有文件级 Diff；
- 回滚和对话历史之间没有建立强关联；
- 验证偏向模型审查，缺少真实构建、测试和浏览器检查；
- 生成代码没有在独立沙箱中执行。

## 12. 关键技术取舍

### 12.1 固定骨架与动态推理分离

选择代码控制执行流、模型完成语义任务。原因是当前阶段更需要稳定复现和调试，而不是最大程度自治。

### 12.2 SSE 而非 WebSocket

当前主要是服务端向前端推送执行事件，SSE 实现简单、兼容 HTTP，也便于流式模型输出。未来如果加入双向实时控制和高频工具交互，再评估 WebSocket 或独立事件总线。

### 12.3 JSON 文件与 SQLite 混合存储

会话和 workspace 使用文件系统，便于查看、导出、快照和调试；模型配置使用 SQLite，便于结构化管理。这个方案适合单机 Demo，但不适合多实例并发，生产化需要迁移到数据库、对象存储和任务队列。

### 12.4 结构化交接优先

Agent 间尽量通过 `brief`、`blueprint`、`review` 等 JSON 产物交接，减少自然语言漂移。解析失败时仍保留 raw 输出用于诊断，但不能把解析失败静默当作成功。

### 12.5 有界修复而非无限自治

审查修复最多执行两轮。无限循环可能持续消耗 token，也不一定提高质量；达到上限后应诚实暴露未解决问题并交给用户决策。

## 14. 后续技术规划

优先级判断遵循三个原则：

1. 先解决正确性和可恢复性，再增加自治程度；
2. 先让现有 Graph 可测试、可观察，再扩展更多 Agent；
3. 优先建设能够同时改善用户体验和工程可靠性的基础设施。

### P0：把 Demo 补成可靠的单机会话系统

#### 1. 多轮意图路由

- 统一后续消息入口；
- 分类 `chat`、`refine`、`modify`、`query`、`rollback`、`pause`、`cancel`；
- 不确定时默认不修改文件；
- 保存完整消息历史并支持刷新后继续。

#### 2. Runtime 基础能力

- 为每次执行引入 run ID；
- 定义 Agent、Node、Tool 的统一状态机；
- 增加节点超时、有限重试和错误分类；
- 支持用户取消和安全停止；
- 保证消息、节点和工具调用幂等。

#### 3. 测试与验证

- 为 Graph 分支、暂停恢复和错误路径增加单元测试；
- 用可控假模型做端到端流程测试；
- 对生成项目执行 HTML 校验、构建检查和浏览器冒烟测试；
- 建立基础回归样例集。

#### 4. 版本可靠性

- 快照增加时间、用户指令、run ID 和摘要；
- 回滚前创建保护快照；
- 回滚后同步文件、预览和会话状态。

### P1：建设可扩展 Agent Runtime

#### 1. Tools Runtime

- 建立 Tool Registry、Schema、权限和执行事件；
- 支持超时、重试、取消和风险审批；
- 文件与命令工具进入隔离环境。

#### 2. Memory 与上下文构建

- 引入 Conversation、Project、Working Memory；
- 建立增量会话摘要；
- 按 Agent 构建最小必要上下文；
- 加入 token budget 和关键信息保护规则。

#### 3. RAG

- 为代码、文档、artifact 和 Skill 建立索引；
- 实现混合检索与重排；
- 输出引用来源并记录检索 trace。

#### 4. Human-in-the-loop

- 支持任意时刻暂停、取消、追加信息；
- 支持计划修改、节点跳过和重做；
- 允许执行中查询状态而不中断主任务。

#### 5. 可观测性

- 统一 trace ID；
- 记录节点耗时、token、成本、错误和工具调用；
- 提供一次运行的 Graph 时间线和失败定位。

### P2：动态 Graph 与生产化

#### 1. 多 Graph Type

- Static Graph：高频、稳定场景；
- Template Graph：根据任务参数展开；
- Dynamic Graph：Planner 生成计划，Runtime 校验后执行；
- Hierarchical Graph：主 Agent 拆分子图；
- Event-driven Graph：外部事件触发节点继续。

动态 Graph 必须经过 Schema 校验、预算检查、循环检测和工具权限校验。

#### 2. 多 Agent 高级编排

- 基于依赖和资源的并发调度；
- Agent 间任务委派与子图生成；
- 多候选方案竞争和 Judge 仲裁；
- 失败节点替代 Agent；
- 基于历史评测选择模型和 Agent 配置。

#### 3. Skills 平台化

- Skill 包版本与依赖；
- 语义匹配和按需加载；
- Skill 与 Tool、输出 Schema、评测集绑定；
- 发布、审核、回滚和使用分析。

#### 4. 生产架构

- PostgreSQL 保存结构化状态；
- 对象存储保存 workspace、artifact 和快照；
- Redis/消息队列承载任务与事件；
- Worker 隔离 Agent 和 Tool 执行；
- 多租户权限、配额、审计和密钥管理。

## 15. 评测体系规划

Agent 系统不能只用“最终页面看起来不错”评价。后续评测分为四层：

| 层级 | 指标示例 |
|---|---|
| 节点质量 | JSON 合法率、字段完整率、事实错误率 |
| Graph 质量 | 路由准确率、无效节点数、恢复成功率 |
| 交付质量 | 构建成功率、需求覆盖率、浏览器测试通过率 |
| 系统效率 | 总耗时、token 成本、并行收益、工具失败率 |

计划维护一组固定需求作为回归集，记录每次 Prompt、模型、Graph 或 Skill 变更前后的结果，避免凭主观感受优化。

## 16. 风险与反思

### Agent 数量不等于效果

多 Agent 会增加调用次数、上下文传递和错误传播。只有当角色边界、交付契约和并行收益明确时，新增 Agent 才有价值。

### 动态程度越高，治理成本越高

动态 Graph 能覆盖更多任务，但会带来循环、越权和成本不可控。正确方向是“受约束的动态”，而不是把控制权全部交给模型。

### Memory 不是无限保存历史

未经治理的历史会造成上下文污染和成本增长。Memory 的核心是选择、压缩、更新和遗忘。

### RAG 不能替代上下文设计

检索结果仍需经过权限、相关性和新鲜度判断。错误召回会让 Agent 更自信地给出错误结论，因此必须记录来源并可评测。

### 当前应优先补可靠性

如果继续投入时间，第一优先级不是增加更多角色或炫目的自治能力，而是补齐多轮意图路由、测试、取消恢复、版本一致性和可观测性。只有底层 Runtime 稳定后，Tools、Memory、RAG 和动态 Graph 才能可靠落地。

## 17. 总结

当前版本验证了一个核心方向：通过确定性 Orchestrator 管理 Graph，让不同 Agent 围绕结构化产物协作，可以把一次模型生成扩展为可观察、可分工、可人工介入的应用生成流程。

项目目前处于多 Agent 工作流 MVP 阶段。它已经具备条件分流、并行执行、结构化交接、人工澄清、审查修复、SSE 事件和基础快照等能力；但距离完整 Agent Runtime 仍缺少多轮意图识别、Tools Runtime、Memory、RAG、上下文压缩、任意时刻中断恢复、权限隔离和系统化评测。

后续演进的重点是把这些能力沉淀为稳定的 Runtime 基础设施，使 Agent 从“能够按流程运行”进一步升级为“能够被可靠调度、被安全约束、被持续评测并在失败后恢复”。
